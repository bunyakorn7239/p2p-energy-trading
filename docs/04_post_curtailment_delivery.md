## 1. ⛔ กฎเหล็ก: ห้ามจับคู่ใหม่

> **การจับคู่เกิดขึ้นตั้งแต่ขั้นป้อน input**
> ผู้ใช้อาจป้อนตามค่าที่ binary search กำหนด หรือป้อนเกินก็ได้
>
> **Safety 2 เป็นเหตุการณ์คนละช่วงเวลา** — เกิดตอน
> **ส่งพลังงานจริง (real power) บนสายส่ง**
>
> ปัญหาทางกายภาพระหว่างส่งมอบ **ต้องไม่ย้อนกลับไปเปิดตลาดที่ปิดไปแล้ว**

**ผลที่ตามมาโดยเจตนา:**

| รายการ | ผลลัพธ์ |
|---|---|
| คู่ค้าที่ผู้ขายยังส่งออกได้ | ✅ **คงเดิมทุกตัวอักษร** — คู่สัญญา ปริมาณ ราคา |
| คู่ค้าของผู้ขายที่ถูก zero-export | ⛔ **ยกเลิกเฉพาะคู่นั้น** |
| การจัดคู่ใหม่ / เกลี่ยพลังงานใหม่ | ❌ **ไม่ทำ** — `changed = []`, `added = []` เสมอ |
| ผู้ซื้อที่เสียคู่ค้าไป | ⚠️ **จบรอบแบบได้ไม่ครบ** ไม่มีใครมาส่งแทน |

👉 การที่ผู้ซื้อ "ขาด" **ไม่ใช่บั๊ก** แต่คือ **ปริมาณพลังงานที่ต้องบันทึกไว้**
ถ้าจับคู่ใหม่ให้อัตโนมัติ ตัวเลขนี้จะถูกกลบหายไปและไม่มีอะไรให้คิดชำระภายหลัง

โค้ดยืนยันตัวเองด้วยฟิลด์
`matching_policy = "FROZEN_NO_REMATCH"` และ `rematch_performed = false`
และหน้าเว็บจะขึ้น ❌ สีแดงทันทีถ้าเผลอมีคู่ถูกเปลี่ยน

## 2. ⭘ กฎการจำลอง Zero-Export

> **บัสของผู้ขายที่ถูก zero-export ต้อง net = 0 kW — ไม่มี sgen และไม่มี load**

เพราะพลังงานที่ผลิตได้ **ใช้เองในบ้านทั้งหมด**
→ ไม่ส่งขึ้นกริด และ **ไม่ดึงจากกริด**

**แยกสองชั้นให้ชัด:**

| ชั้น | ผู้ขายที่ถูกตัด | ฟังก์ชัน |
|---|---|---|
| **ตลาด (market)** | ❌ ไม่ส่งมอบ ไม่มีรายได้ | `matching_seller_list()` |
| **Power flow** | ✅ **คงชื่อไว้ในลิสต์** ตั้ง `sold = unsold = 0` | `pf_seller_list()` |

⚠️ **ห้ามถอดชื่อออกจากลิสต์ `sellers` ที่ส่งเข้า `run_case()`** —
บัสที่ไม่อยู่ในลิสต์จะตกไปเข้า `else` แล้วโดน `create_load(ACTUAL_LOAD_DATA)`
ใส่โหลด 1.169 kW กลับเข้าไป = จำลองว่าบ้านหลังนั้น **ดึงไฟจากกริด**

**ตัวเลขยืนยัน (รันจริง, 12.00 kWh ทุกราย, D ถูกตัด):**

| วิธีจำลอง | Bus 25 | Vmax |
|---|---|---|
| ✅ คงในลิสต์ ตั้งพลังงาน = 0 | sgen 0 · load 0 · **net 0.000000 kW** | **1.035395** |
| ❌ ถอดออกจากลิสต์ | โหลด 1.169 kW โผล่กลับ | 1.032935 |
| | **ส่วนต่าง** | **0.00246 p.u.** |

ระบบรัน **control run** ทั้งสองแบบแล้วส่งกลับใน `zero_export_audit`
เพื่อให้ตรวจได้ ไม่ต้องเชื่อคำอธิบาย
สังเกตว่าแบบผิด **ดูปลอดภัยกว่าความจริง** → ถ้าใช้จะประเมินความเสี่ยงต่ำเกินไป

## 3. ✅ คุณสมบัติที่ควรเขียนลงเปเปอร์

> **การยกเลิกคู่ค้าไม่ทำให้แรงดันเกินอีก**

**เหตุผล:** ใน POST_MATCH กำลังที่ฉีดที่บัสผู้ขาย = `sold + unsold`
ซึ่ง **เท่ากับพลังงานที่ประกาศเสมอ** ส่วนบัสผู้ซื้อรับโหลด = ความต้องการที่ประกาศ
(ผู้ซื้อยังใช้ไฟเท่าเดิม แค่ซื้อส่วนที่ขาดจากกริดแทน)
การยกเลิกคู่ค้าจึงแค่ย้ายพลังงานจากช่อง "ขาย P2P" ไปช่อง "เหลือ"
ของผู้ขายที่ไม่ได้ส่งออกอะไรอยู่แล้ว

**ยืนยันเชิงตัวเลขทุกเคส:** POST_MATCH ของ Phase 2 = Vmax ที่เคลียร์ปัญหาใน
Phase 1 **ทุกหลักทศนิยม**

👉 **การตัดคู่ค้าย้ายเงิน ไม่ย้ายกระแส**

## 4. 📒 บัญชีพลังงานค้าง — **ปริมาณเท่านั้น**

> กฎของบล็อกนี้: บันทึกเป็น **kWh อย่างเดียว**
> ไม่มีราคา ไม่มีจำนวนเงิน ไม่มีสูตรค่าชดเชยหรือค่าปรับ
> ทุกแถวติดสถานะ `PENDING_SETTLEMENT` และหมายเหตุ
> **"จะทำการคิดการชำระเงินเพิ่มเติมภายหลัง"**

### 🛒 ฝั่งผู้ซื้อ — `settlement.buyer_energy_shortfall`

| ฟิลด์ | ความหมาย |
|---|---|
| `buyer` / `seller` | ผู้ซื้อ และผู้ขายที่จับคู่กันไว้ |
| `shortfall_kwh` | พลังงานที่ควรได้ตามสัญญาเดิมแต่ไม่ได้ |
| `status` | `PENDING_SETTLEMENT` |
| `note_th` | จะทำการคิดการชำระเงินเพิ่มเติมภายหลัง |

### ⚡ ฝั่งผู้ขาย — `settlement.seller_energy_undelivered`

| ฟิลด์ | ความหมาย |
|---|---|
| `declared_kwh` | ประกาศไว้ตอนป้อน input |
| `delivered_kwh` | ส่งมอบจริง = **0** (zero-export) |
| `undelivered_p2p_kwh` | ส่วนที่ค้างส่งตาม**สัญญา P2P** ที่ถูกยกเลิก |
| `undelivered_total_kwh` | ส่วนที่**ไม่ได้ป้อนเข้าระบบทั้งหมด** (รวมส่วนเหลือขายกริดที่หายไปด้วย) |
| `buyers_left_short` | รายชื่อผู้ซื้อที่ได้พลังงานไม่ครบเพราะรายนี้ |
| `status` / `note_th` | `PENDING_SETTLEMENT` / จะทำการคิดการชำระเงินเพิ่มเติมภายหลัง |

**ทำไมต้องมี 2 ตัวเลขฝั่งผู้ขาย** — เคส 12.00 kWh ทุกราย D ไม่มีคู่ P2P เลย
(พลังงานทั้งก้อนเป็นส่วนเหลือขายกริด) ถ้ารายงานแค่ `undelivered_p2p_kwh`
จะได้ 0 ซึ่งดูเหมือนไม่มีอะไรค้าง แต่ความจริง D ไม่ได้ป้อน 12.0 kWh เข้าระบบ
ตัวเลข `undelivered_total_kwh` จึงจำเป็น

### ตัวอย่างผลรันจริง

| เคส | ฝั่งผู้ซื้อ | ฝั่งผู้ขาย (D) |
|---|---|---|
| 12.00 ทุกราย | ไม่มีใครขาด | ประกาศ 12.0 · ส่งจริง 0 · ค้าง P2P **0** · ไม่ได้ป้อนรวม **12.0** |
| D กระจุก 50 | J 2.0 · A 12.0 · B 12.0 · G 10.0 · H 10.0 | ประกาศ 50.0 · ส่งจริง 0 · ค้าง P2P **46.0** · ไม่ได้ป้อนรวม **50.0** |
| 24.00 ทุกราย | ไม่มีใครขาด | D และ F: ประกาศ 24.0 · ค้าง P2P 0 · ไม่ได้ป้อนรวม 24.0 (รายละ) |

### 🚩 สิ่งที่ต้องตัดสินใจภายหลัง (ยังไม่เขียนลงโค้ด)

โมดูลนี้ **ไม่ตัดสิน** ว่าฝ่ายใดผิด — แจ้งเตือนของผู้ขายใช้สถานะกลาง
`PENDING_SETTLEMENT` ไม่ใช่ `NO_FAULT_CURTAILMENT` เหมือนเวอร์ชันก่อน
เพราะการชี้ว่าไม่มีความผิดก็เท่ากับตัดสินนโยบายไปแล้วครึ่งหนึ่ง

คำถามที่ต้องตอบเมื่อออกแบบกติกาการชำระเงิน:

1. ผู้ซื้อที่ได้ไม่ครบ ได้รับการชดเชยจากใคร และคิดที่ราคาใด
   (ราคาสัญญาเดิม / ToU / ส่วนต่าง)
2. ประกาศ **เกิน** เพดาน Safety 1 แล้วถูกตัด นับเป็นความผิดของผู้ขายหรือไม่
   — ถ้านับ ต้องแยกจากกรณีประกาศไม่เกินแล้วยังถูกตัด (no-fault)
3. ความเสียหายต่อโครงข่าย จะคิดจากปริมาณ (kWh) หรือจากระดับการละเมิด
   (ΔV เกินกี่ p.u.) หรือทั้งสอง

## 5. 🔁 ลำดับการทำงานเมื่อกดปุ่ม "รัน Safety 2"

```
กดปุ่ม
  │
  ├─ Phase 1 — หาว่าต้องตัดใคร
  │   ├─ รัน POST_MATCH → พบ over-V
  │   ├─ จัดอันดับ ∂Vmax/∂P ของผู้ขายที่ยังส่งออก
  │   ├─ zero-export รายที่สูงสุด (sold = 0, unsold = 0)
  │   └─ รัน PF ยืนยัน → ยังเกิน? วนตัดรายถัดไป
  │
  └─ Phase 2 — ใช้ผลการตัดกับ "คู่เดิม" (ไม่จับคู่ใหม่)
      ├─ order_book : คู่เดิมทุกคู่ + ป้าย DELIVERED / CANCELLED
      ├─ PF BASE      : ฐานอ้างอิงไม่มี PV
      ├─ PF PRE_MATCH : ผู้ขายที่เหลือฉีดเต็มพิกัด (คนถูกตัด = 0)
      ├─ PF POST_MATCH: เท่ากับ Phase 1 เป๊ะ
      └─ ledger       : ปริมาณที่ผู้ซื้อขาด + ปริมาณที่ผู้ขายไม่ได้ส่ง (kWh)
```
