## 1. 🎯 นิยามสั้นที่สุด

> **Zero-Export = ไม่ส่งไฟส่วนเกินขึ้นกริด**
> บ้านหลังนั้นใช้ไฟจาก PV ของตัวเองได้ตามปกติ (**self-consumption อย่างเดียว**)
> แต่ **ไม่มีการขายไฟในตลาด P2P เกิดขึ้น** ในรอบนั้น

หมายเหตุสำคัญ 3 ข้อ:

| ประเด็น | เป็นอย่างไร |
|---|---|
| PV ยังทำงานอยู่ไหม | ✅ ยังทำงาน จ่ายโหลดในบ้านได้เต็มที่ |
| ไฟไหลขึ้นกริดไหม | ❌ ไม่ไหล — คุมให้ net ที่จุดเชื่อมต่อ = 0 W |
| ขายในตลาด P2P ได้ไหม | ❌ ไม่ได้ในรอบนั้น (รายได้ P2P = 0) |

⚠️ **คำที่ต้องระวังเวลาเขียนวิทยานิพนธ์:** พลังงานส่วนที่ถูกตัด
**ไม่ได้ถูกผลิตออกมาแล้วทิ้ง / ไม่ได้ลงกราวด์** — อินเวอร์เตอร์
**เลื่อนจุดทำงานออกจาก MPP ทำให้ไม่ผลิตพลังงานส่วนนั้นตั้งแต่แรก**

## 2. ⚙️ ทำอย่างไรในทางปฏิบัติ — Export Control = 0 W

```
┌──────────┐      ┌───────────┐    ┌──────┐   CT/Meter   ┌──────┐
│ Solar PV │─DC──▶│ Inverter  │─AC─┤ MDB  ├──────╳──────▶│ Grid │
└──────────┘      │ Export    │    └──┬───┘   วัด net    └──────┘
                  │ Ctrl = 0W │       │
                  └─────▲─────┘   โหลดในบ้าน
                        │              │
                        └──── feedback ┘   (สั่งลด P จนกว่า CT อ่าน ≈ 0 W)
```

**ลำดับการทำงาน**

1. CT / smart meter ติดที่ **ขาที่ต่อเข้ากริด** → วัด **net** ที่จุดเชื่อมต่อ
   (ไม่ใช่วัดกำลังผลิตของ PV)
2. ตั้งค่า **Export Control = 0 W** ที่อินเวอร์เตอร์
3. อินเวอร์เตอร์ทำ closed-loop: ถ้า CT อ่านค่าเป็นบวก (มีไฟไหลออก)
   → **เลื่อนจุดทำงาน MPPT ออกจากจุด maximum power**
   → **ดึงกำลังจากแผงน้อยลง** → กำลังที่เหลือพอดีกับโหลดในบ้าน
4. ผลลัพธ์: กำลังที่จุดเชื่อมต่อ ≈ 0 W

**ปรับแค่ P ไม่ยุ่งกับ Q** — วิทยานิพนธ์นี้ควบคุมเฉพาะกำลังจริง (active power)
ไม่ใช้ Volt-VAR / reactive power control
(สอดคล้องกับ IEEE 1547-2018 §4.6.2 "limit active power")

**เคสสุดขั้ว:** ถ้าโหลดในบ้าน = 0 อินเวอร์เตอร์จะถูกกดลงจนจ่าย 0 W
— นี่คือกรณีที่ผู้ขายเสียประโยชน์สูงสุด และเป็นเหตุผลที่ต้องมี
สถานะ **no-fault** ในการคิดเงิน

## 3. 🔬 Smart Inverter — ตามที่เราเขียนไว้ และข้อควรระวัง

**ที่เราเขียนไว้:**
> Smart inverter: ปรับจุดทำงาน solar PV อัตโนมัติ เพื่อให้ solar PV
> จ่ายพลังงานตามพิกัด inverter
> \*\* ขนาด inverter ต้องเล็กกว่า Solar PV จึงจะทำงานกรณีนี้ได้ \*\*

**⚠️ ข้อควรระวังก่อนเอาไปใส่เปเปอร์** — เงื่อนไข "inverter ต้องเล็กกว่า PV"
ใช้กับ **การ clipping แบบ passive** เท่านั้น ต้องแยก 2 กลไกออกจากกัน:

| | Passive clipping | **Commanded curtailment (ที่เราใช้)** |
|---|---|---|
| กลไก | PV ผลิตเกินพิกัด inverter → inverter จ่ายได้แค่ nameplate | สั่ง setpoint จากภายนอก (0 W … P_avail) |
| เงื่อนไข | ต้องมี DC/AC ratio > 1 (inverter เล็กกว่า PV) | **ไม่ต้องมีเงื่อนไขขนาด** ทำได้ทุก setpoint |
| ค่าที่จำกัด | ตายตัวที่ nameplate | ปรับได้อิสระ รวมถึง **0 W** |
| ชื่อทางวิชาการ | clipping / inverter saturation | **CPG / FPPT** · IEEE 1547-2018 limit active power |

👉 **Zero-export ของเรา (P_limit = 0) คือแบบที่สอง** จึงใช้ได้
**ไม่ว่าอินเวอร์เตอร์จะเล็กหรือใหญ่กว่าแผง**
ถ้าเขียนว่า "ต้องเล็กกว่า" กรรมการอาจถามว่า
"แล้วบ้านที่ inverter ใหญ่กว่าแผง สั่ง zero-export ไม่ได้เหรอ" — ได้ครับ

## 5. 🔗 ทำไม zero-export ถึงแก้ over-voltage ได้ (สมการ)

แรงดันที่บัส *i* บนฟีดเดอร์ radial ประมาณได้ด้วย

```
ΔV_i  ≈  ( R_i · P_i  +  X_i · Q_i ) / V_nom
```

- `R_i`, `X_i` = ความต้านทาน/รีแอกแตนซ์**สะสม**จากหม้อแปลงถึงบัส *i*
- `P_i` = กำลังจริงสุทธิที่ฉีดเข้าที่บัสนั้น (ค่าบวก = ส่งออก)

เมื่อสั่ง zero-export ที่ผู้ขาย *s* → `P_s = 0` → พจน์ `R_s · P_s` หายไปทั้งก้อน
เนื่องจากเราคุมเฉพาะ P (`Q` คงเดิม) การลดลงของแรงดันจึงมาจากพจน์ `R·P` เท่านั้น
— และเพราะฟีดเดอร์นี้มี **X/R ≈ 1.25** พจน์ `R·P` ยังมีนัยสำคัญมากพอที่จะแก้ปัญหาได้

**ค่าความไวที่ระบบใช้จัดอันดับ** คือ

```
S_s  =  ∂Vmax / ∂P_s        [p.u. / kWh]
```

คำนวณเชิงตัวเลขในโค้ด: ฉีดเพิ่ม `Δ = 1 kWh` ที่ผู้ขาย *s* → รัน AC power flow →

```
S_s  =  ( Vmax(P_s + Δ) − Vmax(P_s) ) / Δ
```

ค่าที่วัดได้จากเน็ตเวิร์กของเรา (ณ จุดทำงานที่ทุกรายฉีดเท่ากัน):

| Seller | Bus | ตำแหน่ง | S = ∂Vmax/∂P (p.u./kWh) |
|---|---|---|---|
| **D** | 25 | ปลายสาย | **0.001467** ← แรงที่สุด |
| F | 35 | กลาง-ปลาย | 0.001007 |
| E | 32 | กลาง | 0.000814 |
| I | 7 | ต้นสาย | 0.000627 |
| C | 14 | ต้นสาย | 0.000210 ← อ่อนที่สุด |

👉 **D มีอิทธิพลมากกว่า C ถึง ~7 เท่า** การตัด D จึงลดแรงดันได้มากที่สุด
ต่อพลังงาน 1 kWh ที่ต้องเสียไป

## 7. 💻 zero-export ถูกจำลองอย่างไรในโค้ด (และทำไมถึงถูกต้อง)

ในโค้ด `run_case("POST_MATCH", ...)` ของ `server.py`:

```python
seller_sold_kwh[s]   = 0.0     # ยกเลิกการขาย P2P
seller_unsold_kwh[s] = 0.0     # ยกเลิกการขายเข้ากริด (FiT)
# ผลคือไม่มี sgen ที่บัสของผู้ขาย s เลย
```

**ทำไมการตั้ง `sgen = 0` ถึงถูกต้องแบบเป๊ะ ๆ ไม่ใช่การลดรูป:**
คอมเมนต์ในโค้ดเดิม (POST_MATCH load loop) ระบุไว้ว่าบัสของผู้ขาย
**ไม่ใส่ `create_load`** เพราะ *"the seller's PV covers its own load and only
the surplus is exported"*

👉 แปลว่า `seller_energy_kwh` **คือกำลังส่วนเกินสุทธิที่จุดเชื่อมต่ออยู่แล้ว**
ซึ่งเป็นปริมาณเดียวกับที่ export limiter ควบคุม
ดังนั้น zero-export ⇒ net ที่จุดเชื่อมต่อ = 0 ⇒ `sgen = 0` **ตรงกันพอดี**

⚠️ **เงื่อนไขที่เปเปอร์ต้องเขียนให้ชัด** ไม่งั้นข้อป้องกันนี้พัง:
> "ปริมาณที่ผู้ขายประกาศ (offer) นิยามเป็น **net surplus at the connection
> point** หลังหักโหลดภายในบ้านแล้ว"

## 7b. ⭘ กฎการจำลองบัสที่ถูก Zero-Export (สำคัญที่สุด — อย่าทำผิด)

> **`zero-export (no export to grid, self-consumption only!!!)`**

บัสที่ถูกสั่ง zero-export มีค่า **net = 0 kW ที่จุดเชื่อมต่อ (PCC)** แปลว่า

| | ค่า | เหตุผล |
|---|---|---|
| `sgen` (ฉีดเข้าระบบ) | **0 kW** | ไม่ส่งไฟส่วนเกินขึ้นกริด |
| `load` (ดึงจากระบบ) | **0 kW** | PV จ่ายโหลดในบ้านตัวเองพอดี ไม่ต้องดึงจากกริด |
| **net ที่ PCC** | **0 kW** | บ้านหลังนี้ "หายไป" จากมุมมองของโครงข่าย |

### ❌ กับดักที่ต้องระวัง — ห้ามถอด seller ออกจากลิสต์ power flow

ใน `run_case()` ของ `server.py` สิ่งที่วางบนบัสถูกตัดสินจาก **ลิสต์ `sellers`**
ที่ส่งเข้าไป:

```python
elif mode == "POST_MATCH":
    if bidx in seller_bus:
        pass                       # บัสผู้ขาย -> ไม่สร้าง load
    elif bidx in buyer_bus:
        ...
    else:
        pp.create_load(net, bus=bidx, p_mw=orig_p, ...)   # ⚠️ โหลดผีโผล่ตรงนี้
```

ถ้า "ถอด" ผู้ขายที่ถูกตัดออกจากลิสต์ตรง ๆ บัสนั้นจะตกไปที่ `else`
→ **ถูกใส่ `ACTUAL_LOAD_DATA` กลับเข้าไป** = จำลองว่าบ้านหลังนั้น
**ดึงไฟจากกริด** ซึ่ง**ขัดกับนิยาม zero-export**

### ✅ วิธีที่ถูก — แยกเป็นสองชั้น

```
ชั้นตลาด (MATCHING POOL)     ->  ถอดผู้ขายออก   (ไม่มีพลังงานให้ขาย)
ชั้นไฟฟ้า (POWER FLOW LIST)  ->  คงผู้ขายไว้    (ตั้ง sold = unsold = 0)
```

ในโค้ดคือฟังก์ชันคู่นี้ใน `violation_handler.py`:

```python
def pf_seller_list(sellers_all, removed):       # ไฟฟ้า: ครบทุกราย
    return list(sellers_all)

def matching_seller_list(sellers_all, removed): # ตลาด: ตัดออก
    rm = set(removed)
    return [s for s in sellers_all if s not in rm]
```

| วิธีจำลอง | Vmax | ถูก/ผิด |
|---|---|---|
| คงไว้ในลิสต์ + `sgen = 0` (net 0) | **1.035395** | ✅ ถูกตามนิยาม zero-export |
| ถอดออกจากลิสต์ (มีโหลดผี 1.169 kW) | 1.032935 | ❌ ผิด — จำลองเป็นผู้ใช้ไฟ |

ต่างกัน **0.00246 p.u.** — ดูน้อยแต่เป็นความผิดพลาดเชิงนิยาม

### 💡 ผลพลอยได้ที่ยืนยันว่าโมเดลถูก

## 8. 📋 สรุปสั้นสำหรับใส่สไลด์

- **Zero-export** = ตั้ง Export Control ของอินเวอร์เตอร์ = **0 W**
- อินเวอร์เตอร์ **เลื่อน MPPT ออกจากจุด maximum power** → ดึงกำลังจากแผงน้อยลง
- **ปรับแค่ P ไม่ยุ่งกับ Q**
- บ้านนั้น **self-consumption อย่างเดียว ไม่มีการขาย P2P**
- พลังงานส่วนที่ถูกตัด **ไม่เคยถูกผลิต** (ไม่ใช่ผลิตแล้วทิ้ง)
- รองรับด้วย **[Z1]** (กลไก CPG/setpoint) + **[Z2]** (FPPT เป็นมาตรฐาน)
- ในระบบเรา = ตัดผู้ขายที่ **∂Vmax/∂P สูงสุด** ทีละราย จนกว่า Vmax ≤ 1.05
