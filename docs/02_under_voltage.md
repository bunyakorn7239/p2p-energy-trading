# 📘 Under-Voltage (V < 0.95 p.u.) — โน้ตอย่างเดียว ไม่แก้ไขอัตโนมัติ

> **สถานะในระบบ: ADVISORY ONLY** — `js/safety2/underVoltage.js` แสดงคำอธิบาย
> และแนวทางแก้ แต่ไม่สั่งการอะไรกับการจับคู่หรืออินเวอร์เตอร์

---

## 1. 🎯 ทำไมเคสนี้ "เป็นไปได้ยาก" ในระบบ P2P ของเรา

**เหตุผลเชิงฟิสิกส์ — P2P ยกแรงดันขึ้น ไม่ใช่กดลง**

แรงดันตกบนฟีดเดอร์ radial:

```
ΔV  ≈  ( R·P_flow  +  X·Q_flow ) / V_nom
```

โดย `P_flow` = กำลังที่ต้องไหล **จากหม้อแปลงมายังโหลด**

- ตลาด P2P เปิดเฉพาะ **ช่วงกลางวันที่ PV ผลิตไฟ**
- PV ของผู้ขายอยู่ **ในฟีดเดอร์เดียวกับผู้ซื้อ** → ไฟถูกฉีดเข้า **ใกล้จุดโหลด**
- โหลดถูกจ่ายด้วยแหล่งที่อยู่ใกล้ → `P_flow` ที่ต้องวิ่งมาจากต้นสาย **ลดลง**
- `ΔV` ลดลงตาม → **Vmin สูงขึ้น**

👉 พูดง่าย ๆ: **การซื้อขาย P2P คือการเอาแหล่งจ่ายไปวางไว้ข้างโหลด
ซึ่งเป็นวิธีแก้ under-voltage อยู่แล้วโดยธรรมชาติ**
under-voltage จึงเป็นปัญหาของ **ช่วงกลางคืน / ช่วงที่ไม่มี PV** ซึ่งอยู่
**นอกเวลาทำการของตลาด** (ตลาดเดินเฉพาะช่วงกลางวัน)

## 2. 🔬 ตัวเลขยืนยันจากเน็ตเวิร์กของเรา

ทดสอบบน `ieee33bus_network.py` ที่ commit ไว้ โดย **ปิด PV ทั้งหมด (sgen = 0)**
แล้วค่อย ๆ เพิ่มโหลดผู้ซื้อ:

| เงื่อนไข | Σ load (kWh) | Vmin (p.u.) | ผล |
|---|---|---|---|
| โปรไฟล์จริง (peak buyer) | 15.55 | ~0.995 | ✅ ปกติ |
| ดันขึ้นจนถึงขีด | **61.91** | **0.950** | ⚠️ เริ่มละเมิด |
| ดันต่อ (ภาพในสไลด์) | 69.86 | 0.943 | ❌ ละเมิดชัด |

- ต้องใช้โหลดผู้ซื้อ **~10 เท่าของโปรไฟล์จริง** และ **ไม่มี PV เลย**
  จึงจะแตะ 0.95 p.u.
- บัสแรกที่ตกคือ **Bus 20** จุดที่ลึกที่สุดคือปลายกิ่ง **Bus 18/19/22**

👉 นี่คือ **หลักฐานเชิงปริมาณ** ที่ใช้ตอบกรรมการว่า
"ทำไมไม่ออกแบบวิธีแก้ under-voltage" — เพราะในโหมดการทำงานของตลาดนี้
เงื่อนไขนั้นไปไม่ถึง

## 3. 🛠️ ถ้าเกิดขึ้นจริง จะแก้อย่างไร

### แนวทางที่ 1 — จำกัดการใช้โหลด (Load Limiting / Demand Response)

- ลดกำลังที่ดึงลงที่บัสซึ่งแรงดันต่ำสุด จนแรงดันกลับเข้ากรอบ
- เป็น **กระจกเงา (mirror)** ของกฎ over-voltage:
  - over-voltage → คุมฝั่ง **injection** (zero-export ผู้ขาย)
  - under-voltage → คุมฝั่ง **withdrawal** (จำกัดโหลดผู้ซื้อ)
- ใช้ค่าความไวชุดเดียวกันได้ แค่กลับเครื่องหมาย:
  ```
  S_b = ∂Vmin / ∂P_load,b      [p.u. / kWh]
  ```
  ผู้ซื้อที่อยู่ปลายสายจะมี `|S_b|` สูงสุด → จำกัดรายนั้นก่อนได้ผลมากที่สุด

### แนวทางที่ 2 — ย้ายไปจับคู่กับโซนที่มี PV สูง

- ให้แหล่งจ่ายอยู่ใกล้โหลด → ลด **electrical distance** ที่กระแสต้องเดินทาง
- ลด `R·P_flow` โดยลด `R` (ระยะ) แทนที่จะลด `P`
- ⚠️ **ข้อควรระวังทางสถาปัตยกรรม:** การ "ย้ายคู่ค้า" คือการ **re-match**
  ซึ่ง**ข้ามเข้าไปในชั้น market layer** และวิทยานิพนธ์นี้กำหนดไว้ว่า
  ชั้นแก้ปัญหาต้องอยู่ใน **power-flow layer เท่านั้น**
  → ถ้าจะใช้ ต้องทำเป็น **ข้อเสนอแนะเชิงนโยบายสำหรับรอบถัดไป**
  ไม่ใช่การแก้กลางรอบ (มิฉะนั้นจะเสียเวลาตลาดและกระทบผู้เข้าร่วมรายอื่น)

### สิ่งที่ตั้งใจ "ไม่ทำ"

- ❌ ไม่ใช้ reactive power / Volt-VAR — วิทยานิพนธ์นี้เป็น **P-only**
- ❌ ไม่ใช้ OLTC / capacitor bank — เป็นทรัพย์สินของการไฟฟ้า
  อยู่นอกขอบเขตของแพลตฟอร์ม P2P

---

## 4. 📋 สรุปสั้นสำหรับใส่สไลด์

- Under-voltage **แทบเป็นไปไม่ได้** ในตลาดนี้ เพราะ P2P เดินเฉพาะกลางวัน
  และ PV ที่ฉีดใกล้โหลด **ยก Vmin ขึ้น**
- ต้องใช้โหลด **~10 เท่าของจริง + ไม่มี PV** จึงจะแตะ 0.95 p.u.
- ถ้าเกิดจริง แก้ได้ 2 ทาง: **จำกัดโหลด** หรือ **ย้ายไปโซนที่ PV สูง**
- ในระบบจึงตรวจจับและ **แจ้งเตือนอย่างเดียว** ไม่แก้อัตโนมัติ
